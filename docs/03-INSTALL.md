# 通用安装流程

本流程不要求某个引擎、模型、操作系统或推理配方。先复用目标设备已经可用的服务，缺少哪一层就补齐哪一层。端口、目录、模型数量和参数均来自本设备盘点。

## 1. 盘点现状

记录 Codex 使用的是桌面、CLI 还是 IDE，实际引擎版本、配置作用域、原云端 provider、默认模型、认证和完整目录来源。桌面内置引擎可能与 PATH 上的 CLI 不同。

对每个候选本地服务记录：

- 后端名称、实际版本、部署位置与受支持的管理方式。
- 实际加载的模型、served model ID、模型修订、量化和硬件资源。
- 客户端可达地址、API 路径、认证来源、是否已被其他客户端使用。
- Responses、Chat Completions、流式、工具、历史和模态的实际能力。
- 上下文、输出上限、采样默认、推理控制，以及它们的文档和实测依据。

未知写未知。模型名含 reasoning、vision 或某个引擎品牌都不能替代探测。[设备盘点模板](../examples/device-inventory.example.json) 可记录多个后端与模型。

Windows 可用 `scripts/preflight.ps1 -Ports <待检查端口列表>` 做基础只读盘点。Linux、macOS、WSL、容器等使用对应平台工具；不要为遵循此文档硬装 Windows Manager、Node 或某种任务计划机制。

## 2. 确定后端与协议分支

按 [后端矩阵](10-BACKEND-COMPATIBILITY.md) 与 [协议要求](04-LOCAL-RESPONSES.md) 选择：

1. 已满足 Codex 使用的 Responses 契约：优先复用，做必要别名与认证路由。
2. 只有其他 API：实现或选用经过验证的协议兼容层，保持流式、工具和历史语义。
3. 缺少必要能力：明确缺口，保留原云端，不把文本演示当作完整安装。

尚无推理服务时，按选定引擎对应版本的官方安装文档配置模型。硬件、驱动、容器和并行设置由该引擎与目标模型决定，不复制案例命令。部署多个模型时分别记录资源和管理范围。

## 3. 填写路由与能力清单

以 [路由模板](../examples/routes.example.json) 为设计输入，逐个记录客户端别名、实际模型 ID、后端与协议、认证引用、上下文、输出和推理策略。模板不是某个网关的实际配置文件。

推理设置按 [参数规则](11-REASONING-AND-PARAMETERS.md) 确定。可以完全没有推理控制，也可以使用模型默认或已验证的控制。不要为了统一外观增加虚假的强度选项。

保证本地别名与云端 ID 不冲突。只要客户端模型 ID 已能明确选中目标，无需额外创造多个档位别名。未知路由返回错误，不自动改走云端。

## 4. 备份与候选实现

备份本设备将修改的配置、已有目录、服务定义和自有脚本，记录逆向操作。不要把包含凭据的备份入库。不修改登录文件、不复制别的设备账号，也不重置无关插件、MCP 或权限。

选用现有网关或按 [实现契约](../reference/README.md) 生成目标机实现。新增组件只负责它明确拥有的路由与兼容逻辑，不接管无关推理进程。凭据由目标设备本地提供，仓库只保存引用方式与占位模板。

统一菜单方案下，添加未被选中的候选 provider，不先切换全局 model_provider。选择层也可以采用目标客户端已验证的等价方案，但不能仅修改模型名字来假定 provider 自动切换。

使用 ChatGPT 云端登录时参考 [provider 模板](../examples/provider.example.toml)；如果原云端采用 API 密钥或受管网关，沿用其认证机制并相应适配，不能把两种身份混在同一个 Authorization 中。

## 5. 隔离验证

使用目标设备实际 Codex 引擎的独立测试进程与候选路由，保持正在运行的客户端仍使用旧云端。通过本地私有配置引用凭据，不将密钥塞进公开命令行或日志。

先确认候选路径可达，再分别验证：原云端真实回复、每个本地模型回复、工具读随机文件、同聊天续问、认证隔离、错误返回和每个宣告的推理控制。测试可缩小临时工具上下文，但不保存为全局禁用。

如果候选与正式服务端口相同，不结束未知占用进程，给测试选用独立地址。模型服务已存在时不为“干净测试”重启共享服务。

## 6. 完整目录与最小切换

按 [目录流程](05-CATALOG.md) 取得匹配客户端的完整云端元数据，追加目标机实际本地模型。目录和实际路由必须一一对应，保存所有云端字段和隐藏条目。

候选目录存在、可解析且隔离验收通过后，预览并应用最小配置差异。统一 provider 示例中的选择值为：

```toml
# 顶层字段，放在第一个 table 之前。占位值必须替换。
model = "TARGET_EXISTING_CLOUD_DEFAULT"
model_provider = "cloud-local-router"
model_catalog_json = "/ACTUAL/ABSOLUTE/PATH/combined-models.json"
```

Windows 使用目标机实际绝对路径和正确的 TOML 字符串；WSL 使用其实际文件系统与配置目录。不要指望配置自动展开 shell 变量或跨环境路径。

解析 TOML、核对预期差异、写回读回，并确认原云端默认和无关设置保留。自定义本地目录可能替换内置目录，所以不能只写本地模型。

## 7. 平台生命周期

为自己新增的网关选择合适的启动、健康、恢复与停止机制。可以复用平台现有服务管理，也可以按需求随客户端启停。

若服务供多个客户端使用，生命周期必须覆盖这些客户端。不要在退出一个 Codex 窗口后停止共享引擎或网关。客户端层与推理层分别管理。

Windows 需要无窗口时从进程创建方式解决，不能仅依赖 PowerShell 自身的隐藏参数；具体源码见 [Windows 历史案例](../cases/ninfer-windows/README.md)。其他平台不套用其包标识、进程名和 AppModel 事件。

先用独立临时任务或进程验证生命周期逻辑，再在空闲窗口做正式退出/重开。不要主动杀死当前聊天使用的网关来验证自动恢复。

## 8. 验收交付

在用户实际使用的客户端确认模型菜单、默认项和能力控件。没有推理控制的模型应表现为受支持的默认或无控制状态，不能保留另一个模型的强度设置。

执行 [验收清单](06-VERIFICATION.md)，填写 [报告](../examples/installation-report.md)。按模型、后端和功能分别写已验证、失败、未验证或不适用。附上本设备回退方法，保留原云端可用路径。
